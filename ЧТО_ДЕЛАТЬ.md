# Что делать по шагам (короткая версия)

## Шаг 1. Обновить файлы

В папке `F:\Visual Studio\VulkanProxy\INDIANA_AGENT`:

```
git pull
```

(или распаковать архив заново поверх)

**Удали старый лог, чтобы скрипт не прочитал его снова:**

```
del VulkanProxy_diagnostic.log
```

Если файла нет — ничего страшного.

## Шаг 2. Пересобрать DLL

```
powershell -ExecutionPolicy Bypass -File .\build_proxy.ps1
```

Ждём:

```
OK: every spvrw symbol used outside the namespace is qualified or forwarded
Assembling: vk_proxy_thunks.generated.asm
dllmain.cpp
Built: ...vulkan-1.dll
```

Если появилось `FAIL` вместо `OK` — пришли эту строку, сборку не продолжать.

## Шаг 3. Скопировать в игру

Скопировать в папку с игрой (туда, где уже лежит `vulkan-1.dll`):

- `vulkan-1.dll` — только что собранный
- `VulkanProxy.ini`
- папку `spv_replace` (целиком, 3 файла)

Проверить в `VulkanProxy.ini`:

```
UseReplacements=1
StructureMatchFallback=1
FuzzyMatch=1
SelfTest=0
```

## Шаг 4. Запустить игру

Дойти до игрового процесса, постоять 1–2 минуты, выйти через меню.

## Шаг 5. Прочитать лог **в папке игры**

```
cd /d "F:\Indiana.Jones.and.the.Great.Circle.Premium.Edition-InsaneRamZes"
findstr /C:"SPIRV SUMMARY:" VulkanProxy_diagnostic.log
```

Ищем таблицу:

```
SPIRV SUMMARY: per stage - stage | compiled | replaced | close-but-rejected | verdict
SPIRV SUMMARY:   fragment     |    444 |      0 |      0 | no file of this stage in the folder
SPIRV SUMMARY:   compute      |     22 |      3 |      0 | ok
```

**Что уже известно на твоей карте (R7 260X, лог от 25.11):**

```
3 accepted (exact hash), 0 rejected, 1047 shader(s) have no counterpart
per stage: vertex 103 | fragment 87 | compute 11   — все 0 rejected
SELFTEST PASSED 3/3,  named+shuffled 3/3, stripped+shuffled 3/3
```

Вывод: **замены работают, отвергнутых нет**. Три файла на твоей карте подставляются по
точному совпадению байтов — это ожидаемо, потому что папка снята с такой же карты.
На другой карте байты будут другими, и там сработает структурный путь (он проверен:
18/18 в `spv_check`).

**Как читать последнюю колонку:**

| Что видно | Что делать |
|---|---|
| `ok` | всё хорошо, замена работает |
| `ok` у `compute` + `0` в `close-but-rejected` | папка исчерпана: файлов для остальных стадий нет |
| `no file of this stage in the folder` | нормально, для этой стадии файлов нет |
| **`ACTION: a file almost matched`** | **вот это интересно** — пришли мне лог |
| `nothing in this log was rejected by the thresholds` | делать нечего, папка исчерпана |

## Шаг 6 (только если в Шаге 5 было ACTION)

`check_spv_replace.ps1` читает лог **из своей папки**. Раньше он находил старый лог в

# Если игра вылетает (звук есть, потом рабочий стол)

Это отдельная проблема, не связанная с заменой шейдеров. Разбор реального лога
(GTX 1660 Ti) показал:

- в логе **ни одной** строки `SPIRV: shader replacement ACCEPTED` - папка `spv_replace`
  в том запуске вообще не участвовала;
- зато было 26 шейдеров трассировочных стадий (`model=5313/5316`) и 20 "пустышек"
  вместо них;
- падение: `!!! EXCEPTION 0xC0000005 at nvoglv64.dll+...`, чтение по адресу
  `0xFFFFFFFFFFFFFFFF`, кадр `vkCreateShaderModule`.

Причина: у GTX 1660 Ti драйвер сообщает `VK_KHR_ray_tracing_pipeline` (есть), но
`VK_KHR_ray_query` (нет). Прокси отдавал игре **смесь**: часть RT настоящая, часть
виртуальная. Шейдеры трассировочных стадий невозможно переписать, поэтому прокси
возвращал вместо них пустышку, а пустышку нельзя отдавать драйверу.

Что изменено в этой сборке (ничего настраивать не нужно):

1. **RT теперь "всё или ничего"**. Если хотя бы одну часть RT приходится
   виртуализировать, вся RT на этой карте виртуальная - игра просто не собирает
   RT-шейдеры. Смеси больше не бывает.
2. **Пустышки больше не отдаются драйверу.** Если шейдер всё же пришлось заблокировать,
   вместо пустышки драйвер получает настоящий нейтральный модуль, который ничего не
   рисует. Это видно (объект не появляется), но игра не падает.
3. В лог добавлены две строки, по которым всё видно сразу:
   - `RT POLICY: ...` - что именно прокси сказал игре про трассировку и почему;
   - `SPIRV: shader #N is a ray-tracing stage module ...` - почему такие модули
     заменяются нейтральными.

Что делать пользователю с 1660 Ti:

1. Поставить эту сборку `vulkan-1.dll` (и `VulkanProxy.ini` рядом).
2. Удалить старый `VulkanProxy_diagnostic.log`, запустить игру, дать ей дойти до
   меню/игры и, если снова вылетит, прислать новый лог.
3. В новом логе проверить: есть строка `RT POLICY:`; нет строки
   `!!! EXCEPTION 0xC0000005 at nvoglv64.dll`.

Если после этого вылет останется:

1. В `VulkanProxy.ini` поставить `ForceVirtualRt=1` (принудительно "нет RT").
2. Если не помогло - `Mode=software` в секции `[compat]`.
3. Если и это не помогло - вылет уже не в RT; пришлите лог, в нём будет видно
   `this thread's current job` и стек.

# Что нового в сборке v17 (и что читать в логе)

## Одним экраном: блок PROXY SUMMARY

В конце нормального запуска (и при выходе из игры) в лог пишется один блок:

```
PROXY SUMMARY: build       : v17 (Nov 28 2026 ...) | RT all-or-nothing | neutral module instead of FAKE | ...
PROXY SUMMARY: ray tracing : virtual - the game cannot build RT modules on this adapter
PROXY SUMMARY: shaders     : 1050 compiled by the game, 3 replaced from spv_replace
PROXY SUMMARY:   vertex 300 / 1 replaced | fragment 280 / 1 replaced | compute 40 / 1 replaced
PROXY SUMMARY: light       : 12 module(s) touch ray tracing, 12 rewritten to 'no hit', 0 withheld from the driver
PROXY SUMMARY: crashes     : 0 driver crash(es) caught, 0 allocation failure(s)
PROXY SUMMARY: verdict     : healthy - 3 replacement(s) applied, no crash, no out-of-memory
```

Это всё, что нужно для ответа «нормально или нет». Если присылают лог — проси этот блок.
`build` теперь содержит версию **и дату сборки**: по нему видно, какая именно DLL у человека.

## Строка `light` — где теряется свет

- `module(s) touch ray tracing` — сколько шейдеров вообще трогают лучи (считается при
  любом значении `DenyRayTracing`, чтобы число не обнулялось);
- `rewritten to 'no hit'` — столько переписано в «луч ни во что не попал». **Именно они
  и дают чёрные зоны**: шейдер умножает свет на 0;
- `withheld from the driver` — трассировочные стадии, которые прокси не отдал драйверу
  (только их и нельзя переписать — лечится заменой).

Если `rewritten` большое, а `replaced` маленькое — свет теряется из-за нехватки файлов
замен, а не из-за прокси. Лечение — добавить файлы (ниже).

## Как добавить файлы замен (возвращает свет)

1. В `VulkanProxy.ini` поставить `DumpLookupInput=32`.
2. Запустить игру, постоять 1–2 минуты именно **в тёмной зоне**, выйти.
   Нужна полная инвентаризация всех шейдеров — поставь `DumpLookupInput=-1`
   (сохранит ВСЁ, около тысячи файлов и сотни мегабайт).
3. В папке игры появятся `spv_input_<стадия>_<номер>_<хэш>.spv`.
4. Запустить:
   ```
   python tools\spv_light_report.py "F:\...\The Great Circle"
   ```
   Скрипт отсортирует модули по доказательствам: сначала те, что реально считают лучи,
   потом трассировочные стадии, потом «по именам похоже на свет».
5. Для лучших кандидатов он печатает готовое имя файла замены, например:
   ```
   spv_input_4_812_74F939DCE4AEB68A.spv
       -> сохранить замену как: spv_74F939DCE4AEB68A.spv
   ```
6. Положить файл в `spv_replace`, проверить: `spv_check.exe "<spv_replace>" "<путь к spv_input...>"`.
7. Вернуть `DumpLookupInput=0`.

Важно: замена должна быть **эквивалентным шейдером без лучей** (то, что раньше собиралось
на GCN2), а не «любой файл». Если сомневаешься — присылай вывод `spv_light_report.py`,
подскажу, что имеет смысл заменять.

## Лог стал короче в разы

Раньше каждые 64 привязки текстуры писались две строки `RESOURCE CHECKPOINT` — это было
около 90% файла. Теперь пишутся только:
- первые 4 привязки (доказательство, что путь жив);
- `RESOURCE FAILED` — ошибка привязки;
- `RESOURCE SLOW ... elapsed=...` — привязка медленнее 100 мс (именно они подвешивают игру);
- `VerboseResourceK=N` — если нужно сердцебиение раз в N тысяч привязок (по умолчанию 0).

## DenyRayTracing теперь действительно работает

Раньше он читался и писался в лог, но нигде не использовался.
- `DenyRayTracing=1` (по умолчанию) — решает железо: что драйвер не умеет, блокируется.
- `DenyRayTracing=0` — «хочу настоящий RT на этой карте»: RT-модули не блокируются и не
  переписываются вообще. Только для карт, которые правда умеют RT.

# Что показал лог от 28 ноября (v17) — и что изменилось в v18

## Лог прочитан целиком, вот его факты

- карта: **AMD Radeon R7 200 Series**, драйвер Vulkan 1.2.178, RT нет вообще
  (`ray_tracing_pipeline=0 ray_query=0`, режим `SOFTWARE_COMPAT`);
- игра отдала **1000 шейдерных модулей**, прокси **переписал 100** ray-query шейдеров в
  «луч ни во что не попал». Здесь и теряется свет: шейдер умножает освещение на результат
  луча;
- из папки `spv_replace` применилось **3 файла** — ровно те 3, что в ней лежат;
- ни одного `CAUGHT driver crash`, ни одной ошибки памяти, ни одной FAKE-замены (кроме
  одной штуки, о которой ниже);
- **лог обрывается** на `vkCreateSwapchainKHR`. Ни `DLL_PROCESS_DETACH`, ни отчёта нет —
  игру закрыли из панели задач или она упала.

## Что это значит для «заменить все шейдеры»

Полная замена всех 1000 модулей **не нужна и не поможет**: 900 из них работают и без
трассировки. Свет теряют именно те **100** переписанных ray-query шейдеров. Замену имеет
смысл делать для них.

И ещё одно, важное: файл замены — это SPIR-V **без лучей**. Сам прокси такой уже делает
(это и есть переписывание в «no hit»), и результат — та же темнота. Значит «заменить все»
без понимания, что должно быть в замене, даст ровно то, что есть сейчас. Поэтому:

## План на v18 (по шагам)

1. `DumpLookupInput=-1` — прокси сохранит **все** модули игры в папку с игрой
   (около тысячи файлов, сотни мегабайт; потом вернуть `0`).
2. `python tools\spv_light_report.py "<папка игры>" --all` — покажет полную картину: какие
   модули считают лучи, какие нет, и готовые имена файлов замены.
3. Прислать мне этот вывод (или хотя бы верхнюю часть). По нему видно, **в каких шейдерах**
   живёт свет в тёмной зоне, и тогда замена будет осмысленной, а не «лишь бы все».
4. Если хочется проверить одну гипотезу до всего этого: уберите `vulkan-1.dll` из папки
   игры (переименуйте в `vulkan-1.dll.bak`) и запустите игру без прокси.
   - игра не запускается или падает → без замены света не будет вообще, темнота — не наша;
   - игра запускается и **в тёмной зоне так же темно** → прокси не виноват, темнота в самой
     игре/на этой карте;
   - игра запускается и **в тёмной зоне светло** → да, это наш переписанный шейдер, и замена
     его вылечит.

## Что уже исправлено в v18

- **отчёт теперь печатается и после первого кадра** (через 8 секунд), а не только при
  выгрузке DLL — лог больше не может кончиться пустотой;
- **лог стал короче примерно в 10 раз**: 12 701 строка `SPVTRACE ACTIVE_RESOURCE` (по строке
  на каждый дескриптор, и одни и те же 512 дескрипторов заново на каждый вызов) заменена
  одной строкой `ACTIVE_BINDING_DIGEST` на пайплайн. По-дескрипторный список пишется только
  для модулей из `spv_replace` или при `Verbose=1`;
- `SHADER stats` больше не пишет обманчивое `denied=0` — теперь рядом стоит
  `ray-query-rewritten=N`;
- лимит в 16 дампов `-1` больше не молчит (раньше 17-й шейдер просто не сохранялся).

# SoftwareRT: почему это не «включить галочку», и что уже сделано (v19)

Ты просил «полноценный SoftwareRT». Прежде чем писать трассировщик, надо было выяснить
один факт, и я его выяснил по коду и по твоему логу.

## Проблема: игра не даёт нам геометрию

В прокси все функции трассировки лучей — **пустые заглушки**. Они возвращают «успех» и
ничего не делают, в том числе `vkCmdBuildAccelerationStructuresKHR` — именно там игра
передаёт **все вершины сцены**. Мы их молча выбрасываем.

Из твоего лога: строки `PROXY RT fallback via GIPA: vkCmdBuildAccelerationStructuresKHR`
означают «прокси выдал игре адрес функции-заглушки», а не «игра её вызвала». Реальных
вызовов в логе нет — проверить было нечем, потому что заглушки не считают вызовы.

Вывод: **сейчас у прокси нет ни одного треугольника сцены.** «Полноценный SoftwareRT» без
этого невозможен в принципе — трассировать нечего.

## Что сделано в v19 (шаг 1 из SoftwareRT)

Теперь заглушки **считают**, что игра реально присылает, и в конце лога печатают одну
честную строку:

```
SOFTWARE RT: AS built N time(s) (M indirect), K geometr(ies), ~V vertices; vertex data addressable: yes/no
SOFTWARE RT: traceRays X, RT pipelines Y, AS objects Z
```

или, если игра вообще не строила ускоряющих структур:

```
SOFTWARE RT: the game never created or built an acceleration structure and never traced rays -
there is no geometry to trace here, so software ray tracing cannot change the picture
```

Ничего в поведении драйвера не изменилось — это чистое измерение. Зато следующий шаг
будет опираться на факт, а не на догадку.

## Три возможных исхода и что каждый значит

| Что покажет лог | Что это значит | Что делаем дальше |
|---|---|---|
| AS не строятся вообще | игра рисует только растеризацией, а свет считает через ray query по данным, которых у нас нет | SoftwareRT не поможет; возвращаемся к замене 100 ray-query шейдеров |
| AS строятся, вершины **читаемы** (`bufferDeviceAddress`) | у нас есть геометрия сцены | делаем шаг 2: таблица треугольников + трассировка и подмена ray-query результатов |
| AS строятся, но вершины **нечитаемы** | адреса буферов недоступны | сначала придётся ловить `vkGetBufferDeviceAddress`, иначе трассировать нечего |

## Честно про объём работы

Шаг 2 (когда геометрия есть) — это: собрать треугольники из AS, реализовать обход
(BVH или грубый перебор), вызывать его для каждого фрагмента... при этом вызов идёт
**из GPU-шейдера**, а не из прокси. Значит нужен ещё канал «шейдер спрашивает — CPU
отвечает», то есть вычислительный проход + буферы. Это большая работа, сопоставимая с
отдельным проектом, и на GCN2 она упрётся в производительность: 100 шейдеров, считающих
свет лучами, на каждом кадре.

Поэтому порядок такой: сначала измерение (v19), потом — по факту — либо трассировщик,
либо замена шейдеров, которая дешевле и, судя по логу (100 переписанных модулей), даёт
тот же визуальный результат быстрее.

# Вердикт по логу v19 (28 ноября, 22:56) — путь SoftwareRT закрыт

## Что показал лог

```
SOFTWARE RT: the game never created or built an acceleration structure and never traced rays -
there is no geometry to trace here, so software ray tracing cannot change the picture
```

Дополнительно:
- `bufferDeviceAddress = 1` — адреса буферов читать **можно**, дело не в этом;
- игра запрашивает расширения у драйвера, но список реальных расширений GCN2 RT не содержит,
  и **ни одного** `vkCreateAccelerationStructureKHR` / `vkCmdBuildAccelerationStructuresKHR` /
  `vkCmdTraceRaysKHR` игра не вызвала (в логе только «выдан адрес функции», а не «вызвано»);
- `1043` модуля, из них `189` переписаны в «луч ни во что не попал», замен применено `3`;
- отчёт напечатался сам после первого кадра — то, ради чего делался A4. Работает;
- лог: `9025` строк вместо `22037` — тише в 2,4 раза.

## Почему SoftwareRT на этой машине невозможен

Трассировщику нужны треугольники мира. Их даёт только построение ускоряющей структуры,
и игра его не делает: она заранее спрашивает у драйвера, есть ли трассировка, не получает
и рисует сцену обычной растеризацией, а свет считает rayonquery-шейдерами по данным,
которые нам не передаются.

Значит «полноценный SoftwareRT» здесь — это не программный трассировщик, а переписывание
логики освещения в 189 шейдерах. Это уже не про прокси.

## Что осталось реальным рычагом

1. **Замена этих 189 шейдеров.** Не «всех 1000», а именно тех, что считают свет.
   `DumpLookupInput=-1` + `python tools\spv_light_report.py "<папка игры>" --all`
